# EHR connections (IntakeQ + Tebra)

Clinsync pulls clients from **IntakeQ** and patient charts from **Tebra** and
reconciles them (`src/lib/ehr-sync.ts`). Credentials are entered by an admin on
**Settings → EHR Connections**, encrypted at rest (AES-256-GCM, `IDENTITY_ENCRYPTION_KEY`),
never shown again, and decrypted only server-side by the connector factory
(`src/connectors/index.ts`).

## Credentials

| Field | What it is | Where to find it |
|---|---|---|
| IntakeQ API key | Account-level key, sent as the `X-Auth-Key` header | IntakeQ: **More → Settings → Integrations → Developer API**. Requires an IntakeQ/PracticeQ admin. |
| Tebra customer key | Account-level key that enables SOAP API access | Generated by a Tebra **System Administrator** (Tebra help: "Get Started: Tebra SOAP APIs" → *Get Customer Key*). |
| Tebra API user | A Tebra login (email) used only for the API | Create a dedicated Tebra user for Clinsync. |
| Tebra API password | That user's password | Set when creating the user. |

**Tebra needs all three** (customer key + user + password) on every call — the key alone does
not authenticate, and Settings only shows Tebra as configured once all three are saved.

### Permissions

- **IntakeQ:** the key has the account's access; there are no per-key scopes.
- **Tebra:** the API user needs security permissions to read patients and practices (a missing
  permission shows up as *"accepted the login, but the API user is missing a required
  permission"*). To use **Add New Patient** with a live Tebra, it also needs permission to
  create patients. A System Administrator sets these.

## Rate limits

- **IntakeQ:** standard plan is **10 requests/minute, 500/day**. A sync costs 1 request per 100
  clients plus **2 requests per new client** (intake summary + full intake). Clinsync retries a
  429 up to 3 attempts, honouring `Retry-After`; beyond that the sync stops with a
  "rate limit reached" message — run it again later or ask IntakeQ to raise the limit.
  Progress is kept: clients already imported are skipped next time. The **first** sync of a
  practice with many existing IntakeQ clients can exceed the daily quota (e.g. 300 new clients
  ≈ 600 requests) and need several runs.
- **Tebra:** Clinsync spaces SOAP calls **≥ 1 second apart** and retries 429/502/503/504.
  Tebra recommends polling no more often than every 5–15 minutes. A sync makes one
  `GetPatients` call (all patients) regardless of patient count.
- Every call has a 15 s timeout and at most 3 attempts. "Sync now" may run up to 5 minutes.

## What is pulled

**IntakeQ** (`/clients`, `/intakes/summary`, `/intakes/{id}`): name, DOB, city, postal code,
phone, email; from the most recent submitted intake, best-effort by question text: referral
type (question mentions "referr…"), availability ("availab…"), contact preference
("preferred … contact"), consent signed (any signed consent form), and rating-scale totals
(questions naming PHQ-9 / GAD-7 / PCL-5 / MDQ **and** "score"/"total" with a numeric answer).
Questionnaires are practice-specific, so check these mappings against your real forms.

**Tebra** (SOAP 2.1 `GetPatients`): ID, name, DOB, city, ZIP, email, primary care physician
(or default rendering provider) → "current provider".

**Not pulled from Tebra:** diagnoses and medications. The SOAP 2.1 API has no per-patient
medication or problem list (diagnoses exist only per encounter). The live connector reports
this, and sync **leaves existing diagnoses/medications untouched** instead of clearing them.

Sync rules (unchanged): a new IntakeQ client with an exact name + DOB match in Tebra goes to the
**Identity Matching** queue; one with no match becomes a new patient; already-linked patients get
only their Tebra-sourced fields refreshed. Staff-owned fields are never touched.

## Mocks vs. live

- **Production** (`NODE_ENV=production` or `VERCEL_ENV=production`): **live connectors only**.
  With nothing configured, sync fails with **"EHR connections are not configured"** and Add New
  Patient returns 503. The demo mocks are never used, even if `EHR_USE_MOCKS` is set.
- **Development / tests:** set `EHR_USE_MOCKS=1` to use the in-repo demo connectors. The Vitest
  setup sets it. Without it, dev behaves like production.

## Testing a connection

1. **In the app:** Settings → EHR Connections → **Test connection** (admin only). IntakeQ is
   checked with a `/clients` name search that matches nobody (no patient data moved); Tebra
   with `GetPractices`. Each side reports *Connected*, *Not configured*, or a safe error
   message (credentials and vendor error text are never shown or logged).
2. **From a terminal** (owner, real credentials in the environment — never in a file in the repo):

   ```sh
   INTAKEQ_API_KEY=... TEBRA_CUSTOMER_KEY=... TEBRA_USER=... TEBRA_PASSWORD=... npm run ehr:check
   # add `-- --no-counts` to only validate credentials (1 call per vendor)
   ```

   Prints `OK` / `FAILED` per vendor and client/patient **counts** only. Exit code 0 = all
   configured vendors passed, 1 = a failure, 2 = nothing configured.
3. Then **Sync now** and check the counts it reports, the Patients list, and the Identity
   Matching queue.

## Verified vs. not yet verified

Verified against the live Kareo 2.1 service with deliberately invalid credentials: the
envelope is accepted, an invalid key comes back as `SecurityResponse` `CustomerKeyValid=false`
(→ "rejected the credentials"), and `GetPatients` needs a `Filter` element. IntakeQ returns
401 for an invalid key.

Needs a run with real credentials: the response shapes of successful calls (date formats,
the intake field mappings above), whether `GetPatients` caps how many records it returns for
large practices, `GetPatient` (it returned an internal fault for invalid credentials, so its
happy path is unconfirmed), and `CreatePatient` (writes a real chart; used only by Add New
Patient, and only when the account has exactly one active practice).
